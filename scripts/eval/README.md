# 디자인 시스템 MCP 평가 (2026-11-25)

## 실행 방법

저장소 루트에서 실행한다. 먼저 `pnpm --filter @internal/design-system build:mcp`, `pnpm --filter @internal/design-system-linter build`, `pnpm --filter mcp build` 가 필요하다.

| 명령 | 내용 | 비용 |
|---|---|---|
| `node scripts/eval/lib/self-check.mjs` | 타입 검사 판정기가 틀린 코드를 거르는지 확인 | 없음 |
| `node scripts/eval/mcp-benchmark.mjs --tokenizer <js-tiktoken 경로>` | 정확성, 충족률, 토큰, 스타일 제안, 오류 처리 | 없음 |
| `node scripts/eval/mcp-agent-eval.mjs --runs 3 [--baseline <이전 서버>]` | 같은 UI 과제를 조건별로 에이전트에게 시켜 채점 | 모델 호출 |

에이전트 평가는 `--out` 폴더에 저장된 응답을 다시 호출하지 않는다. 새로 재려면 새 폴더를 지정한다.

## 해석할 때의 한계

- **개선 후 서버가 에이전트 평가에서 개선 전보다 낫다는 근거는 없다.** 통과 수는 오히려 낮다(10/12 대 12/12). 실패 2건은 모두 `<Flex as="form" onSubmit>` 이었다. `Box` 는 `as` 를 바꿔도 DOM prop 타입이 `div` 로 남는 디자인 시스템의 제약이며, 서버 응답은 이를 알려 주지 않는다. 표본이 작아 우연일 수 있다.
- 숫자 토큰을 숫자로 돌려주는 수정은 예비 실행(조건당 4회)에서 발견했다. 따라서 과제 4개는 완전히 분리된 시험 데이터가 아니다.
- 과제는 4개이고 모델은 하나다. 조건 간 큰 차이(문서 0/12 대 MCP 10~12/12)는 참고할 수 있지만 2~3건 차이는 구분하지 못한다.
- 통과는 타입 검사, import, 요구 컴포넌트 사용만 본다. 화면 모양, 접근성, 동작은 채점하지 않았다. 토큰 우회(`rawStyles`)는 모든 조건에서 0이어서 변별력이 없었다.
- 소스 탐색 조건의 실패 3건은 한 과제에서 숫자 토큰을 문자열로 쓴 것이다.
- 오프라인 벤치마크는 개선 작업과 함께 작성했다. 정답은 타입 검사기와 스타일 소스지만, 새 응답 형식(`groups`, `excludedSprinkles`)을 해석하는 코드가 들어 있다. 정확성은 리터럴 값과 prop 존재만 검사하며 기본값과 설명은 검사하지 않는다.
- 충족률에서 남은 누락은 대부분 `as="p"` 처럼 임의의 HTML 태그를 받는 prop 이다.
